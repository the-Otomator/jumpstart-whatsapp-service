# WhatsApp entitlement and session keys

This document describes how another trusted service provisions and authorizes a WhatsApp device against `jumpstart-whatsapp-service`. It is intentionally written for callers that do not share this repository's implementation context.

## Why entitlement matters

Both `GET /connect/:sessionKey` and `POST /api/sessions/:sessionKey/start` call `validateOrg` before exposing or starting a pairing flow. A total entitlement miss returns an authorization failure: the connect route renders the HTTP 403 error page instead of a QR, and the API route returns a 403 response.

The outer validation guard fails open when a database failure throws: it logs the exception and returns `valid: true` so a transient database outage does not take the service offline. This is an availability choice, not an entitlement source. Individual Supabase calls can also return an `error` value rather than throw; callers must not assume every database failure takes the outer fail-open path.

Before evaluating entitlement, the service attempts to resolve the supplied key through `whatsapp_devices.session_key`. When a row is found, subsequent checks use that row's real `whatsapp_devices.org_id`. When no device row exists, the raw supplied key is evaluated as the organization identity.

## Entitlement evaluation order

The implementation reads the following four subscription/slot sources in order. The first complete passing path authorizes the request.

| Order | Source | Required columns and predicate | Pass condition |
|---:|---|---|---|
| 1 | `central_subscriptions` | `org_id = resolvedOrgId`, `status = 'active'`; reads `product_id`, `plan`, `user_email`, `organization_name` | An active row exists and its product passes source 2. |
| 2 | `products` | `id = central_subscriptions.product_id`; reads `slug` | `slug = 'whatsapp-service'`. This completes the central-subscription path. |
| 3 | `org_system_subscriptions` plus `system_license_plans` | Subscription: `organization_id = resolvedOrgId`, `system_code = 'jumpstart'`, `status = 'active'`; reads `plan_code`, `metadata`. Plan: `system_code = 'jumpstart'`, `code = plan_code`; reads `features`. | `floor(features.whatsapp_devices_included) + floor(metadata.whatsapp_extra_devices) >= 1`, with negative/invalid values clamped to zero. |
| 4 | `partner_org_slots` | `org_id = resolvedOrgId`, `status = 'active'`; reads `partner_name` | An active slot exists. The resulting plan is `partner/<partner_name>`. |

If every source misses, `validateOrg` returns `valid: false`: the connect page is HTTP 403 with no QR, and session start is rejected.

## Session-key conventions

Treat a session key as an opaque identifier after it is created. Never derive authorization from a label or phone number.

| Owner/path | Convention | Notes |
|---|---|---|
| JumpStart legacy/single-device | The organization UUID itself | Multi-device callers should store and pass the exact `whatsapp_devices.session_key` instead. |
| WorkMatch canonical device | `wm-<orgUUID>-<8char>` | `<orgUUID>` is the real WorkMatch organization UUID. `<8char>` is a stable per-device suffix generated by a trusted provisioning backend. |
| WorkMatch legacy | `wm-workmatch-<rand>` | Grandfathered only. Do not create this shape for a new device. Historical suffixes may be timestamp-derived rather than random UUID fragments. |
| Generic partner registration | `{partnerName}-<rawId>` | The registration route leaves an ID unchanged when it already starts with the partner prefix. WorkMatch is the special case whose configured prefix is `wm-`, not `workmatch-`. |

`partner_org_slots.org_id` historically mixes two identity types: real organization UUIDs and raw session keys. New WorkMatch provisioning must use one active tenant-level row keyed by the real organization UUID. Existing raw-key rows are compatibility records, not a model to copy.

## Canonical WorkMatch provisioning

Provisioning must be coordinated by a trusted server-side WorkMatch/Otomator backend. Do not perform these operations from browser code.

1. Obtain the real WorkMatch organization UUID and the stable WorkMatch device ID.
2. Generate a canonical session key in the form `wm-<orgUUID>-<8char>`; retain the same key for retries of the same device operation.
3. In one trusted transaction, create or update the Hub `whatsapp_devices` row:
   - `org_id` = the real organization UUID
   - `session_key` = the canonical key
   - `source_system` = `workmatch`
   - `source_tenant_id` = the real organization UUID
   - `source_device_id` = the WorkMatch device ID
   - device label/provider/status fields as required by the owning workflow
4. In that same transaction, ensure exactly one active `partner_org_slots` row with `org_id` equal to the real organization UUID and `partner_name = 'workmatch'`.
5. Persist the exact session key in the WorkMatch device/config record. Downstream requests must forward it unchanged.
6. From a trusted backend, call the authenticated session-start API with the exact session key and a valid absolute HTTPS webhook URL. Never omit the webhook URL.
7. Direct the authorized operator to `/connect/<sessionKey>` to scan the QR. Do not implement a retry action by purging authentication state.
8. Use lifecycle callbacks and the registry row to observe `qr`, `connected`, `disconnected`, and error states. Provider acceptance is not proof that a handset received a message.

The current `register-partner` route is a legacy/compatibility registration mechanism; it is not sufficient for canonical WorkMatch provisioning because it writes only `partner_org_slots` and does not create `whatsapp_devices`. In addition, passing a bare WorkMatch UUID to the current route produces `wm-<UUID>` rather than the canonical bare-UUID tenant slot. Canonical WorkMatch provisioning therefore belongs in the trusted transactional provisioning path described above.

## Partner registration endpoint

```http
POST /api/sessions/:orgId/register-partner
Authorization: Bearer <service-api-secret>
x-partner-key: <partner-registration-secret>
Content-Type: application/json

{"partnerName":"workmatch"}
```

The route is under the service-wide `/api` authentication middleware, so both server-side credentials are required in production. `x-partner-key` is compared with the server's `PARTNER_REGISTRATION_KEY`.

The partner registration key is a server-side secret. It must never appear in browser/mobile code, a public environment variable, logs, analytics, error reports, documentation examples containing real values, or a committed configuration file. Call this endpoint only from a trusted backend.

Prefix behavior:

- `partnerName = 'workmatch'` uses prefix `wm-`.
- Other partners use `{partnerName}-`.
- If `:orgId` already starts with the selected prefix, it is stored unchanged; otherwise the prefix is prepended.
- The route upserts `partner_org_slots(org_id, partner_name, status='active')` on conflict with `org_id`.

Use this endpoint only for an explicitly approved compatibility registration. It does not create a device registry row, session credentials, session metadata, or a webhook URL, and it does not start a session.

## Troubleshooting

| Symptom | Likely cause | What to check |
|---|---|---|
| connect page shows the 403 error page instead of a QR | Total entitlement miss; often a legacy key has no device row and no raw-key partner slot | Exact HTTP status; `whatsapp_devices.session_key`; resolved `org_id`; the four entitlement sources in order; service log `No WhatsApp entitlement found for org`. |
| Connect page is HTTP 200 but no QR appears | Entitlement passed, but session start failed or no active QR exists | Session status endpoint; session directory; `creds.json`; `meta.json`; a valid `webhookUrl`; server error code such as `WEBHOOK_URL_REQUIRED`. |
| Start returns 502 | Provider/session start raised a server-side error | Container log for the exact session key and request time. Do not treat 502 itself as the cause. Common recoverable causes differ from `loggedOut (401)`. |
| `WEBHOOK_URL_REQUIRED` | Start or restore was attempted without a valid absolute HTTP(S) webhook URL | Request body and stored `meta.json`. Repair a live session only through the authenticated no-restart webhook endpoint. |
| Entitlement exists for the organization but a legacy key still gets 403 | The legacy key has no `whatsapp_devices` mapping, so validation never resolves it to the real UUID | Add/adopt the device in the trusted registry workflow, or use an explicitly approved temporary legacy slot; do not guess from labels. |
| Two devices share a label but behave differently | Labels are not identities | Compare exact `session_key`, `whatsapp_devices.id`, and `source_device_id`. Never operate by label or phone number. |
| A QR session repeatedly emits unauthorized webhook errors | Orphan session metadata points at the wrong/retired consumer or its session key is absent from the consumer registry | Exact stored webhook target, consumer auth contract, and registry mapping. Registration entitlement alone does not repair webhook delivery. |
| Database is unavailable but the request passes validation | A thrown database error reached `validateOrg`'s fail-open catch | Correlate the validation error log and database availability; do not interpret the pass as proof of entitlement. |

## Migration guidance for legacy WorkMatch artifacts

- Preserve a genuinely connected legacy Baileys identity unless the owner explicitly schedules a phone re-pair. A cosmetic key rename is not worth taking a working phone offline.
- A connected legacy key can be adopted by a `whatsapp_devices` row that maps the exact key to the real organization UUID. Once that mapping and the bare-UUID tenant slot are proven, the raw-key slot is redundant and may be retired in a separately authorized data change.
- An unpaired legacy QR session with no `creds.json` can be abandoned in favor of canonical provisioning without losing a paired identity. Cleanup and a new QR scan still require explicit operational authorization.
- Never rename a session directory or hand-edit `partner_org_slots`/`whatsapp_devices` to simulate migration. Use the owning provisioning workflow and independently verify the resulting service and registry state.
